# SuzuEmojy 资源数据库设计与跨端同步规范

本文档记录 SuzuEmojy 在 Android 手机端资源数据库架构设计及与 PC 端的跨端同步规范。

---

## 【落地决策记录】

### 1. Hash 计算规则（已由 PC 代码实证）
- **静态图（PNG/JPG/WEBP 等）**: 
  - 计算 **PIL `img.convert('RGBA').tobytes()` 的 MD5**。
  - 该计算必须在标准化重新编码为最终 PNG **之前**进行。
  - **Android 对应实现**: 使用 `BitmapFactory.Options` 显式设置 `inPremultiplied = false`、`inPreferredConfig = Bitmap.Config.ARGB_8888`、`inScaled = false` 进行解码，通过 `copyPixelsToBuffer` 提取原始 RGBA 字节流计算 MD5，确保与 Python PIL 字节流完全一致。
- **动态图（GIF）**:
  - 直接计算 **GIF 文件本身的完整二进制字节流 MD5**。

### 2. `sync_key` 格式与同步身份
- **格式规范**:
  - 静态图: `p:<md5>` (例如 `p:92b93896345dc57b4b461983afe3ac48`)
  - 动态图: `f:<md5>` (例如 `f:4892a649b58ca67dbfc0768007b6b9ce`)
- **唯一身份标识**: `sync_key` 作为跨端同步的唯一身份主键/唯一索引。
- **本地文件名隔离**: 文件名（如 `20260702121038188211.png` 时间戳）仅作为设备本地物理文件管理的本地身份，**严禁**参与跨端同步比对。

### 3. 【重要限制】动图跨端去重与转码边界
- **核心限制原因**: PC 端的动图 hash 基于 FFmpeg 动态两步调色板转码输出，而跨平台/不同版本的 FFmpeg 编码输出具有非确定性（Non-deterministic）。
- **手机端约束**:
  - 手机端 v1 **不实现任何动图转码**，仅接受现成的 GIF 文件并直接提取文件字节流 MD5。
  - **严禁**后续在手机端加入 WebM/动态WebP 转 GIF 的本地转码，否则会彻底破坏双端跨端去重与同步一致性。
  - 该限制若需解除，前提是 PC 与 Android 双端统一升级为“首帧像素 MD5 + 帧数”特征方案（归入 v2 架构议题）。

### 4. 同步数据源基准
- **数据源判定**: 双端同步以 **`features.db`** (SQLite) 为权威准绳。
- **历史文件说明**: `hashes.json` 仅为 PC 端早期演进过程中的历史兼容双写产物，不作为任何同步与对账的依据。

### 5. 资源删除策略
- **删除分类**: 默认仅删除分类本身及 `resource_categories` 关联表中的关系映射，不触碰资源实体与物理文件。
- **连带物理删除**: 仅当用户在 UI 上显式勾选“彻底删除该分类内表情”二次确认时，遍历该分类下的表情，对**不属于其他任何分类**的孤立资源执行数据库记录及磁盘物理文件的永久删除（保持与 PC 端行为完全一致）。

### 6. 资源存储目录与文件系统强一致性
- **存储位置**: 必须保存在 Android **应用私有存储目录** (`context.filesDir` / `data/data/...`)。
- **隔离保护**: 外部系统图库（MediaStore 扫描器）与第三方手机管家/清理大师均不可见且无权删除，杜绝因外部清理导致 DB 记录与本地文件系统失步，确保强一致性。

### 7. 手机端数据库架构选型
- **架构**: 手机端采用 **Room 单库多表** (`suzu_emojy.db`)，包含 `resources`、`categories`、`resource_categories`、`recent_history` 四张核心表。
- **选型理由**:
  - PC 端采用 5 库分离历史包袱较重，而移动端跨表操作（如级联删除、分类移动、多对多关联）必须在单库事务内才能获得真正的 ACID 原子性与外键约束保障。
  - 在功能维度、分类逻辑与去重效果上，与 PC 端完全等价且性能更优。

### 8. EXIF 旋转策略与 PNG 重编码无损性验证
- **EXIF 旋转策略**: v1 与 PC 端保持完全一致，不主动套用 EXIF 旋转矩阵，以原始解出的像素数据直接入库与计算 Hash；v2 如需引入方向自纠正，必须双端同步修改。
- **PNG 重编码无损性**: 经过 `CleanerParityTest` 实验验证，Android 端将 RGBA Bitmap 通过 `Bitmap.compress(PNG)` 重新编码后再读回，解出的 RGBA 像素与二次计算的 MD5 均与原始基准值 100% 逐位吻合，证明 PNG 重编码过程对像素 Hash 具备绝对无损性。
